<p>整段出口被标记，往往是团队扩号之后才突然出现的：昨天还好好的，今天半个组的号一起弹验证。这时候靠猜没用，得有一棵能往下走的故障树——从"整段被标"这个根节点开始，分成地址属性、共享污染、并发行为、上游线路四条支路，每条支路给出可查的证据和对应的处置动作。这篇按故障树的方式组织，顺带说清一号一环境怎么落地、双 ISP 家宽怎么做冗余、包月和按量按人数怎么定。</p>

<h2>一、根节点：整段被标记的四种成因</h2>
<p>看到"整段一起出问题"，先别急着换供应商。同时出问题说明变量是共用的，而共用变量无非四类：地址属性、同段共享、并发行为、上游线路。四类的排查成本差别很大，从最便宜的查起。</p>
<h3>成因一：地址属性本来就不是住宅</h3>
<p>供应商交付的段看着像家宽，实际挂在机房 ASN 下，或者被情报库标成托管。这类问题一查就清楚，用 whois 看 ASN 归属、用两三个情报库交叉看标签。属性不对的话，无论怎么优化用法都白费，只能换址。</p>
<h3>成因二：同段被大量账号共用</h3>
<p>一个 C 段卖出几十条，几十个团队同时挂着跑，即便每条地址各自独立，整段的对外行为特征也会趋同。平台侧看到的是一整段地址在相似时段做相似动作，这种模式识别与单条地址干不干净关系不大。</p>
<h3>成因三：并发与频率超出正常家用特征</h3>
<p>家庭宽带不会同时维持几十条长连接、也不会全天候每几秒一次请求。团队把号集中在几条出口上跑自动化任务，流量特征很快就偏离住宅样本，这是最容易自己造成的问题，也是最容易改的。</p>
<p>还有一种容易漏掉的成因是上游线路本身被降权。供应商的上游是二级运营商或转售商，整条链路在某些时段被限速或 QoS 降级。表现为延迟忽高忽低、丢包集中在固定时段，与账号行为无关。这类问题查 ASN 查不出来，只能靠分时段测量发现规律。</p>

<h2>二、往下分叉：整段故障还是单号故障</h2>
<p>根节点确定之后，第二步是判断范围。整段一起坏和个别号坏，处置方式完全相反：前者要换环境，后者要查单个号的使用记录。判断方法是用三个样本做交叉验证。</p>
<h3>样本一：同段不同号</h3>
<p>从同一段里挑三个号，在同一时段做同样的操作。三个都出问题，指向段级别；只有一个出问题，指向该号自身。这一步能把范围缩小一半。</p>
<h3>样本二：同号不同段</h3>
<p>把一个出问题的号换到另一条干净的段上再操作一次。换段后恢复正常，说明是该段的问题；换段后仍异常，说明问题跟着号走，与该号的历史行为、绑定的支付方式或设备指纹有关。</p>
<p>第三个样本是只挂连接不发请求，观察延迟与丢包。如果纯挂着也抖，说明是线路层面的问题，与请求行为无关。这一步用来区分"被行为触发"和"被线路拖累"。</p>

<h2>三、多账号同时接入的三条并发支路</h2>
<p>团队扩号时最常犯的错是把新号都塞进同一条出口，理由是"先跑起来再说"。并发一上来，前面所有干净度工作都会被抵消。一号一环境不是口号，它对应三条具体的隔离要求。</p>
<h3>支路一：出口隔离，每个号固定一条地址</h3>
<p>最基础的一层。每个账号绑定一条固定的住宅出口，地址不与他号共用、不随会话漂移。落地方式是给每条地址建一个独立的客户端配置或独立容器，配置里写死出口，不让它自动切换。</p>
<h3>支路二：会话隔离，Cookie 与存储不交叉</h3>
<p>同一台机器上跑多个号，最容易出的问题是浏览器配置文件混用。要用独立的用户数据目录，每个号一个，退出时不要共用缓存。容器或独立系统账户都可以，关键是存储路径彼此不可见。</p>
<h3>支路三：时段隔离，避免同秒同动作</h3>
<p>十几个号在同一秒发出同样的请求，这个特征比地址本身更显眼。做法很简单：把任务错开，每个号的操作时间加几十秒到几分钟的随机偏移，批量任务的启动时间也拉开。这一条不花钱，效果却明显。</p>

<h2>四、双 ISP 家宽的冗余怎么接</h2>
<p>单条出口断了就是全员停摆，所以团队规模上去之后要考虑冗余。双 ISP 的意思是有两条来自不同运营商的线路，一条主用一条备用，故障时能切换。这里的关键不是"有两条"，而是"两条真的不同源"。</p>
<h3>冗余要跨运营商，而不是跨账号</h3>
<p>同一个运营商开两条宽带，上游机房往往是同一处，一起断的概率很高。要选两家不同的一级运营商，或者至少确保 ASN 不同。切换策略上，主线路丢包超过阈值时自动切，切回来要人工确认，避免来回抖动。</p>
<h3>切换要保留登录连续性</h3>
<p>备用线路的出口地址与主线路不同，切换后账号看到的登录地会变。为了减少影响，备用线路尽量选同一城市、同一运营商的另一段地址，让变化幅度小一些。切换频率也要控制，一天切好几次比不切更糟。</p>

<h2>五、按这五步走，别跳步</h2>
<p>故障树的价值在于顺序。跳过前面的步骤直接换供应商，往往换完问题照旧，因为根因没找到。按下面五步走，每一步都有明确产出。</p>
<h3>第一步查属性，第二步定范围</h3>
<p>先用 whois 和情报库确认段属性，再用三个样本交叉确定是段级还是号级。这两步加起来不超过一小时，却能决定后面所有动作的方向。属性不对直接换，范围是号级就别动整段。</p>
<h3>第三步看并发，第四步测线路，第五步才谈采购</h3>
<p>并发问题靠错峰和隔离解决，线路问题靠分时段测量确认。前四步都排除之后，才轮到讨论是不是该换供应商、该按包月还是按量买。采购是最后手段，不是第一反应。计费方式上，人数少、在线时间短的按量更合适，人数多、全天在线的包月更稳，具体按实际在线小时折算。</p>

<h2>常见问答</h2>
<h3>整段被标记之后，这个段还能救回来吗？</h3>
<p>答：短期很难。段级标记通常需要时间沉淀，靠换用法、降频率在几天内恢复的可能性不大。比较现实的做法是先换到新段维持业务，把旧段放一段时间再小流量试探。指望立刻恢复，往往会耽误更久。</p>
<h3>一号一环境是不是必须一人一台机器？</h3>
<p>答：不必。隔离的核心是出口、存储、凭据三者不交叉，一台机器上用独立容器或独立系统账户同样能做到。真正要避免的是多个号共用同一个浏览器配置文件、同一条出口、同一套登录凭据。</p>
<h3>双 ISP 是不是一定要买两条？</h3>
<p>答：看业务对中断的容忍度。只有一两个人用、断了可以等，单线加一条便宜的按量备用就够了；十几个人同时在线、断了直接影响交付，就值得上双线。冗余的成本要跟停机损失比，不是越多越好。</p>
<h3>按人数定计费，怎么算才不吃亏？</h3>
<p>答：先统计两件事：同时在线的峰值人数、每天的有效在线小时。峰值决定需要几条出口，在线小时决定包月还是按量。只按人头买而不看在线时长，容易出现人多的组买少了、人少的组买多了。</p>
